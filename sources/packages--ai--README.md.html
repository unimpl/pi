 102 ## Quick Start
 103 
 104 You build a `Models` collection of providers and stream through it. The quickest start registers every built-in provider; apps that care about bundle size register individual providers instead (see [Provider Factories](#provider-factories) and [Bundling and Tree Shaking](#bundling-and-tree-shaking)).
 105 
 106 ```typescript
 107 import { Type, type Context, type Tool } from '@earendil-works/pi-ai';
 108 import { builtinModels } from '@earendil-works/pi-ai/providers/all';
 109 
 110 // A Models collection with every built-in provider registered
 111 const models = builtinModels();
 112 
 113 // Sync lookup against the collection
 114 const model = models.getModel('openai', 'gpt-4o-mini')!;
 115 
 116 // Define tools with TypeBox schemas for type safety and validation
 117 const tools: Tool[] = [{
 118   name: 'get_time',
 119   description: 'Get the current time',
 120   parameters: Type.Object({
 121     timezone: Type.Optional(Type.String({ description: 'Optional timezone (e.g., America/New_York)' }))
 122   })
 123 }];
 124 
 125 // Build a conversation context (easily serializable and transferable between models)
 126 const context: Context = {
 127   systemPrompt: 'You are a helpful assistant.',
 128   messages: [{ role: 'user', content: 'What time is it?', timestamp: Date.now() }],
 129   tools
 130 };
 131 
 132 // Option 1: Streaming with all event types.
 133 // Auth resolves through the provider (OPENAI_API_KEY from the environment here).
 134 const s = models.stream(model, context);
 135 
 136 for await (const event of s) {
 137   switch (event.type) {
 138     case 'start':
 139       console.log(`Starting with ${event.partial.model}`);
 140       break;
 141     case 'text_start':
 142       console.log('\n[Text started]');
 143       break;
 144     case 'text_delta':
 145       process.stdout.write(event.delta);
 146       break;
 147     case 'text_end':
 148       console.log('\n[Text ended]');
 149       break;
 150     case 'thinking_start':
 151       console.log('[Model is thinking...]');
 152       break;
 153     case 'thinking_delta':
 154       process.stdout.write(event.delta);
 155       break;
 156     case 'thinking_end':
 157       console.log('[Thinking complete]');
 158       break;
 159     case 'toolcall_start':
 160       console.log(`\n[Tool call started: index ${event.contentIndex}]`);
 161       break;
 162     case 'toolcall_delta':
 163       // Partial tool arguments are being streamed
 164       const partialCall = event.partial.content[event.contentIndex];
 165       if (partialCall.type === 'toolCall') {
 166         console.log(`[Streaming args for ${partialCall.name}]`);
 167       }
 168       break;
 169     case 'toolcall_end':
 170       console.log(`\nTool called: ${event.toolCall.name}`);
 171       console.log(`Arguments: ${JSON.stringify(event.toolCall.arguments)}`);
 172       break;
 173     case 'done':
 174       console.log(`\nFinished: ${event.reason}`);
 175       break;
 176     case 'error':
 177       console.error(`Error: ${event.error.errorMessage}`);
 178       break;
 179   }
 180 }
 181 
 182 // Get the final message after streaming, add it to the context
 183 const finalMessage = await s.result();
 184 context.messages.push(finalMessage);
 185 
 186 // Handle tool calls if any
 187 const toolCalls = finalMessage.content.filter(b => b.type === 'toolCall');
 188 for (const call of toolCalls) {
 189   const result = call.name === 'get_time'
 190     ? new Date().toLocaleString('en-US', {
 191         timeZone: call.arguments.timezone || 'UTC',
 192         dateStyle: 'full',
 193         timeStyle: 'long'
 194       })
 195     : 'Unknown tool';
 196 
 197   // Add tool result to context (supports text and images)
 198   context.messages.push({
 199     role: 'toolResult',
 200     toolCallId: call.id,
 201     toolName: call.name,
 202     content: [{ type: 'text', text: result }],
 203     isError: false,
 204     timestamp: Date.now()
 205   });
 206 }
 207 
 208 // Continue if there were tool calls
 209 if (toolCalls.length > 0) {
 210   const continuation = await models.complete(model, context);
 211   context.messages.push(continuation);
 212   console.log('After tool execution:', continuation.content);
 213 }
 214 
 215 console.log(`Total tokens: ${finalMessage.usage.input} in, ${finalMessage.usage.output} out`);
 216 console.log(`Cost: $${finalMessage.usage.cost.total.toFixed(4)}`);
 217 
 218 // Option 2: Get complete response without streaming
 219 const response = await models.complete(model, context);
 220 
 221 for (const block of response.content) {
 222   if (block.type === 'text') {
 223     console.log(block.text);
 224   } else if (block.type === 'toolCall') {
 225     console.log(`Tool: ${block.name}(${JSON.stringify(block.arguments)})`);
 226   }
 227 }
 228 ```

 232 ## Providers and Models
 233 
 234 A **provider** is the runtime unit: it owns its model catalog, its auth (API key resolution, OAuth flows), and its stream behavior. A `Models` collection holds providers and routes every request to the provider that owns the model.
 235 
 236 Providers internally share **API implementations** (the wire protocols): Anthropic models use `anthropic-messages`, OpenAI uses `openai-responses`, while xAI, Groq, Cerebras, OpenRouter, and most others share `openai-completions`. Mixed-API providers (GitHub Copilot, OpenCode Zen) dispatch per model.
 237 
 238 ### Provider Factories
 239 
 240 For apps that only need specific providers, there is one factory per built-in provider, each a subpath import that pulls only that provider's catalog:
 241 
 242 ```typescript
 243 import { anthropicProvider } from '@earendil-works/pi-ai/providers/anthropic';
 244 import { openaiProvider } from '@earendil-works/pi-ai/providers/openai';
 245 import { openrouterProvider } from '@earendil-works/pi-ai/providers/openrouter';
 246 import { amazonBedrockProvider } from '@earendil-works/pi-ai/providers/amazon-bedrock';
 247 // ...one module per provider in the Supported Providers list
 248 
 249 const models = createModels();
 250 models.setProvider(anthropicProvider());
 251 models.setProvider(openrouterProvider());
 252 ```
 253 
 254 Provider factories import their model catalog and a lazy API wrapper. They do not import other providers. With bundler code splitting, SDK implementations (`@anthropic-ai/sdk`, `openai`, `@google/genai`, etc.) stay in lazy chunks loaded on the first request to a model of that API.

 256 ### All Built-in Providers
 257 
 258 For apps that want everything (as in Quick Start):
 259 
 260 ```typescript
 261 import { builtinModels } from '@earendil-works/pi-ai/providers/all';
 262 
 263 const models = builtinModels(); // a Models collection with every built-in provider registered

It is the heavy, explicit entrypoint. `builtinModels()` accepts the same options as `createModels()` (`credentials`, `authContext`); `builtinProviders()` returns the provider array if you want to register them on your own collection.

 268 ### Querying Models
 269 
 270 Reads are synchronous and return the last-known lists:
 271 
 272 ```typescript
 273 const providers = models.getProviders();           // registered Provider objects
 274 const provider = models.getProvider('anthropic');  // one provider
 275 
 276 const all = models.getModels();                    // every model across providers
 277 const anthropicModels = models.getModels('anthropic');
 278 const model = models.getModel('anthropic', 'claude-sonnet-4-5');
 279 
 280 for (const m of anthropicModels) {
 281   console.log(`${m.id}: ${m.name}`);
 282   console.log(`  API: ${m.api}`);
 283   console.log(`  Context: ${m.contextWindow} tokens`);
 284   console.log(`  Vision: ${m.input.includes('image')}`);
 285   console.log(`  Reasoning: ${m.reasoning}`);
 286 }
 287 ```
 288 
 289 Dynamically listed models are typed `Model<Api>`. Narrow with the `hasApi()` guard when you need API-specific option typing:
 290 
 291 ```typescript
 292 import { hasApi } from '@earendil-works/pi-ai';
 293 
 294 const m = models.getModel('anthropic', 'claude-sonnet-4-5');
 295 if (m && hasApi(m, 'anthropic-messages')) {
 296   // m: Model<'anthropic-messages'> — stream options fully typed
 297   models.stream(m, context, { thinkingEnabled: true, thinkingBudgetTokens: 2048 });
 298 }
 299 ```

 326 ## Auth
 327 
 328 Every provider owns its auth: how API keys resolve (stored credentials, environment variables, ambient sources like AWS profiles or gcloud ADC) and, where supported, OAuth login/refresh flows.
 329 
 330 ### How Auth Resolves
 331 
 332 When you call `models.stream()`, the collection resolves auth through the owning provider and merges it into the request. Explicit per-request values always win:
 333 
 334 ```typescript
 335 // Resolved through the provider (env var, stored credential, OAuth token):
 336 await models.complete(model, context);
 337 
 338 // Explicit key wins over anything the provider would resolve:
 339 await models.complete(model, context, { apiKey: 'sk-explicit' });
 340 ```
 341 
 342 You can inspect resolution without making a request. Pass a provider ID for provider-scoped auth, or a model to include its static `model.headers`:
 343 
 344 ```typescript
 345 const providerAuth = await models.getAuth(model.provider);
 346 const modelAuth = await models.getAuth(model);
 347 
 348 if (modelAuth) {
 349   console.log(`configured via ${modelAuth.source}`); // e.g. "ANTHROPIC_API_KEY", "OAuth", "stored credential"
 350   console.log(modelAuth.auth.headers);              // Provider auth headers + model.headers
 351 } else {
 352   console.log('not configured');
 353 }
 354 ```
 355 
 356 Both overloads resolve credentials, refresh expired OAuth when necessary, and may return an auth-derived `apiKey`, `headers`, or `baseUrl`. `getAuth()` resolves `undefined` for unconfigured providers and rejects with `ModelsError` when something is actually broken (`"oauth"`: token refresh failed, credential preserved for re-login; `"auth"`: key resolution or credential store failure). Request paths surface the same failures as stream errors.
 357 
 358 `getAuth()`, `checkAuth()`, `getAvailable()`, login, and logout accept optional caller cancellation through their existing options or interaction objects and remain unbounded when no signal is supplied. Provider `login`, `ApiKeyAuth.check`, `ApiKeyAuth.resolve`, and `OAuthAuth.refresh` implementations always receive a concrete signal and must honor it for blocking work.
 359 
 360 ### Transforming Request Headers
 361 
 362 `Models.stream()`, `complete()`, `streamSimple()`, and `completeSimple()` accept a Models-only `transformHeaders` option. It runs once after provider auth, `model.headers`, and explicit `options.headers` have been merged, but before provider dispatch:
 363 
 364 ```typescript
 365 const response = await models.completeSimple(model, context, {
 366   headers: { "X-Client": "my-app" },
 367   transformHeaders: async (headers) => ({
 368     ...headers,
 369     "X-Request-ID": crypto.randomUUID(),
 370   }),
 371 });
 372 ```
 373 
 374 The ordering is:
 375 
 376 ```text
 377 provider auth headers -> model.headers -> explicit options.headers -> transformHeaders -> Provider.stream*()
 378 ```
 379 
 380 Header names are merged case-insensitively. Explicit headers override auth/model headers, and the transform has final control; returning `null` for a header suppresses lower-level defaults that support deletion.
 381 
 382 `transformHeaders` belongs to `Models`, not `Provider`. A `Models` implementation must consume it and remove it before calling `Provider.stream*()`. Provider implementations continue receiving ordinary `ApiStreamOptions` or `SimpleStreamOptions` and never handle the transform themselves. Use this option instead of calling `getAuth(model)` before `stream*()`, which would resolve request auth twice.

 384 ### Credential Store
 385 
 386 Stored credentials (API keys entered interactively, OAuth tokens) live in a `CredentialStore` — one type-tagged credential per provider. pi-ai ships an in-memory default; apps inject persistent storage:
 387 
 388 ```typescript
 389 import { createModels, type CredentialStore } from '@earendil-works/pi-ai';
 390 
 391 const models = createModels({ credentials: myFileBackedStore });
 392 // builtinModels() takes the same options:
 393 // const models = builtinModels({ credentials: myFileBackedStore });
 394 ```
 395 
 396 The contract is small: `read(providerId)`, `list()` for non-secret `{ providerId, type }` metadata, `modify(providerId, fn)` (the only write path — a serialized read-modify-write), and `delete(providerId)`. Each operation accepts optional cancellation options. Enumeration must not resolve secrets or execute configured key commands. OAuth token refresh runs inside `modify`, so concurrent requests and processes cannot double-refresh a rotated token. A stored credential *owns* its provider: environment variables are only consulted when nothing is stored, and a failed refresh never silently falls back to an env key.
 397 
 398 API-key credentials use the same discriminator as pi's `auth.json` and can carry provider-scoped env/config values:
 399 
 400 ```typescript
 401 const credential = {
 402   type: 'api_key',
 403   key: '...',
 404   env: {
 405     CLOUDFLARE_ACCOUNT_ID: 'account-id',
 406     CLOUDFLARE_GATEWAY_ID: 'gateway-id'
 407   }
 408 } as const;
 409 ```

 460 ## Tools
 461 
 462 Tools enable LLMs to interact with external systems. This library uses TypeBox schemas for type-safe tool definitions with automatic validation using TypeBox's built-in validator and value conversion utilities. TypeBox schemas can be serialized and deserialized as plain JSON, making them ideal for distributed systems.
 463 
 464 ### Defining Tools
 465 
 466 ```typescript
 467 import { Type, type Tool, StringEnum } from '@earendil-works/pi-ai';
 468 
 469 // Define tool parameters with TypeBox
 470 const weatherTool: Tool = {
 471   name: 'get_weather',
 472   description: 'Get current weather for a location',
 473   parameters: Type.Object({
 474     location: Type.String({ description: 'City name or coordinates' }),
 475     units: StringEnum(['celsius', 'fahrenheit'], { default: 'celsius' })
 476   })
 477 };
 478 
 479 // Note: For Google API compatibility, use StringEnum helper instead of Type.Enum
 480 // Type.Enum generates anyOf/const patterns that Google doesn't support
 481 
 482 const bookMeetingTool: Tool = {
 483   name: 'book_meeting',
 484   description: 'Schedule a meeting',
 485   parameters: Type.Object({
 486     title: Type.String({ minLength: 1 }),
 487     startTime: Type.String({ format: 'date-time' }),
 488     endTime: Type.String({ format: 'date-time' }),
 489     attendees: Type.Array(Type.String({ format: 'email' }), { minItems: 1 })
 490   })
 491 };
 492 ```

 494 ### Constrained Sampling for Tools
 495 
 496 Tools can opt in to provider-side constrained sampling. For JSON-schema tools, `strict: 'prefer'` uses provider-side strict schema enforcement when supported and otherwise falls back to normal tool calling. `strict: 'require'` fails the request when the active provider/model cannot honor it. Set `constrainedSampling: false` to explicitly opt out; it behaves the same as omitting the field.
 497 
 498 ```typescript
 499 const strictTool: Tool = {
 500   name: 'edit_file',
 501   description: 'Edit a file',
 502   parameters: Type.Object({
 503     path: Type.String(),
 504     content: Type.String()
 505   }, { additionalProperties: false }),
 506   constrainedSampling: { type: 'json_schema', strict: 'prefer' }
 507 };
 508 ```
 509 
 510 Strict JSON-schema constrained sampling is supported for OpenAI, Anthropic, supported Amazon Bedrock Converse models, Mistral, and Gemini 3 tool calls through the Google Generative AI and Vertex adapters. Google uses `VALIDATED` function-calling mode (or `ANY` when explicitly requested); earlier Gemini versions fall back for `strict: 'prefer'` and reject `strict: 'require'` because they do not enforce required parameters. Bedrock strict-tool capability is generated from model structured-output metadata; custom Bedrock models can override `compat.supportsStrictMode`. OpenAI Responses and Chat Completions can also emit grammar-constrained custom tools with OpenAI Lark or regex grammar variants. If multiple OpenAI variants are supplied, Lark is preferred over regex. Grammar constraints are enforced when the active model supports grammar tools; otherwise the tool falls back to normal function/JSON-schema handling. Grammar tool capability is model metadata: the generated catalog sets `compat.supportsOpenAIGrammarTools` for GPT-5+ models on endpoints that pass OpenAI custom tools through (OpenAI, OpenAI Codex, Azure OpenAI Responses, GitHub Copilot, opencode, and Cloudflare AI Gateway). OpenAI rejects `type: "custom"` tools for pre-GPT-5 models, and gateways that normalize tool schemas (e.g. OpenRouter) mangle them, so the flag stays off elsewhere. Custom model definitions can opt in via `compat`. Grammar-capable models reject grammar configurations without a non-empty supported variant.  576 ### Streaming Tool Calls with Partial JSON
 577 
 578 During streaming, tool call arguments are progressively parsed as they arrive. This enables real-time UI updates before the complete arguments are available:
 579 
 580 ```typescript
 581 const s = models.stream(model, context);
 582 
 583 for await (const event of s) {
 584   if (event.type === 'toolcall_delta') {
 585     const toolCall = event.partial.content[event.contentIndex];
 586 
 587     // toolCall.arguments contains partially parsed JSON during streaming
 588     // This allows for progressive UI updates
 589     if (toolCall.type === 'toolCall' && toolCall.arguments) {
 590       // BE DEFENSIVE: arguments may be incomplete
 591       // Example: Show file path being written even before content is complete
 592       if (toolCall.name === 'write_file' && toolCall.arguments.path) {
 593         console.log(`Writing to: ${toolCall.arguments.path}`);
 594 
 595         // Content might be partial or missing
 596         if (toolCall.arguments.content) {
 597           console.log(`Content preview: ${toolCall.arguments.content.substring(0, 100)}...`);
 598         }
 599       }
 600     }
 601   }
 602 
 603   if (event.type === 'toolcall_end') {
 604     // Here toolCall.arguments is complete (but not yet validated)
 605     const toolCall = event.toolCall;
 606     console.log(`Tool completed: ${toolCall.name}`, toolCall.arguments);
 607   }
 608 }
 609 ```
 610 
 611 **Important notes about partial tool arguments:**
 612 - During `toolcall_delta` events, `arguments` contains the best-effort parse of partial JSON
 613 - Fields may be missing or incomplete - always check for existence before use
 614 - String values may be truncated mid-word
 615 - Arrays may be incomplete
 616 - Nested objects may be partially populated
 617 - At minimum, `arguments` will be an empty object `{}`, never `undefined`
 618 - The Google provider does not support function call streaming. Instead, you will receive a single `toolcall_delta` event with the full arguments.

 654 ### Complete Event Reference
 655 
 656 Successful generation follows `start → updates* → done`. A failure after generation starts follows `start → updates* → error`. Request setup may fail before generation starts, in which case the stream contains only `error`; `done` and update events are invalid before `start`. Direct API `streamSimple()` calls throw synchronously when request auth is missing.
 657 
 658 Every non-terminal event's `partial` is the shared live response-so-far helper. It is intentionally not an event-time snapshot: providers may mutate the same message and content blocks as generation advances, including while older events wait in the stream queue. Inspect it when handling an event instead of retaining it as historical state. Text and ordinary thinking blocks are empty when their `*_start` event is emitted and grow only through matching `*_delta` events until the authoritative `*_end`; redacted thinking may be complete at start and emit no deltas. Tool-call arguments at `toolcall_start` are provider-specific; `toolcall_delta` carries subsequent JSON updates.
 659 
 660 All streaming events emitted during assistant message generation:
 661 
 662 | Event Type | Description | Key Properties |
 663 |------------|-------------|----------------|
 664 | `start` | Stream begins | `partial`: Initial assistant message structure |
 665 | `text_start` | Text block starts | `contentIndex`: Position in content array |
 666 | `text_delta` | Text chunk received | `delta`: New text, `contentIndex`: Position |
 667 | `text_end` | Text block complete | `content`: Full text, `contentIndex`: Position |
 668 | `thinking_start` | Thinking block starts | `contentIndex`: Position in content array |
 669 | `thinking_delta` | Thinking chunk received | `delta`: New text, `contentIndex`: Position |
 670 | `thinking_end` | Thinking block complete | `content`: Full thinking, `contentIndex`: Position |
 671 | `toolcall_start` | Tool call begins | `contentIndex`: Position in content array |
 672 | `toolcall_delta` | Tool arguments streaming | `delta`: JSON chunk, `partial.content[contentIndex].arguments`: Partial parsed args |
 673 | `toolcall_end` | Tool call complete | `toolCall`: Complete, but not schema-validated, tool call with `id`, `name`, `arguments` |
 674 | `done` | Stream complete | `reason`: Stop reason ("stop", "length", "toolUse"), `message`: Final assistant message |
 675 | `error` | Error occurred | `reason`: Error type ("error" or "aborted"), `error`: AssistantMessage with partial content |
 676 
 677 Streaming events for different content blocks are not guaranteed to be contiguous. Providers may emit deltas for text, thinking, and tool calls in the same upstream chunk, and pi may surface corresponding events interleaved, for example `text_start`, `text_delta`, `toolcall_start`, `text_delta`, `toolcall_delta`. Consumers must use `contentIndex` to associate each delta/end event with its block and must not assume that a block's `*_start`/`*_delta`/`*_end` sequence is uninterrupted by events for other blocks.
 678 
 679 ### Compact Assistant Message Frames
 680 
 681 `AssistantMessageFrameEncoder` converts one stream into compact, persistable `AssistantMessageFrame` values. Create one encoder per stream and feed it every event in order. The encoder understands that `partial` is live: a block-start event consumed after the provider has already queued later deltas snapshots the current block once, and covered queued text/thinking deltas produce no duplicate frame. It retains only per-open-block counters plus, temporarily, the raw prefix needed to synchronize an already-advanced tool call. It never clones the growing full partial per token.
 682 
 683 The start frame contains message metadata with empty content. Text and thinking frames store each generated character at most once before the authoritative end frame. Tool calls that were already advanced when their start event was consumed use one compact JSON checkpoint before ordinary deltas resume. Terminal `done` and `error` events produce no frame because final message settlement is separate. A pre-generation `error` therefore produces no frames.
 684 
 685 `reduceAssistantMessageFrames()` is the canonical pure reducer. It reconstructs text, thinking, and tool-call arguments, including interleaved blocks identified by `contentIndex`, and rejects malformed sequences. It performs a single pass over the iterable and returns `undefined` when there is no start frame. End frames replace blocks with the provider's authoritative completed content and metadata. The reducer does not validate tool arguments against a TypeBox schema; call `validateToolCall` before execution.
 686 
 687 ```typescript
 688 import {
 689   AssistantMessageFrameEncoder,
 690   reduceAssistantMessageFrames,
 691   type AssistantMessageFrame,
 692 } from '@earendil-works/pi-ai';
 693 
 694 const encoder = new AssistantMessageFrameEncoder();
 695 const frames: AssistantMessageFrame[] = [];
 696 for await (const event of s) {
 697   const frame = encoder.encode(event);
 698   if (frame) frames.push(frame);
 699 }
 700 
 701 const reconstructedPartial = reduceAssistantMessageFrames(frames);
 702 const finalMessage = await s.result(); // Persist terminal settlement separately.
 703 ```
 704 
 705 An encoder rejects duplicate starts, updates before start, `done` before start, events after a terminal event, duplicate block starts, and block-kind mismatches. An `error` before start is valid and returns no frame.

 808 ### Notes and Limitations
 809 
 810 - Image models live in `ImagesModels` collections, chat models in `Models` collections; the two are separate surfaces.
 811 - Use `generateImages()`, not the chat/stream APIs.
 812 - Image-generation models do not participate in tool calling.
 813 - Outputs are returned in `AssistantImages.output` and can include both base64-encoded `ImageContent` blocks and `TextContent` blocks.

 818 - At the moment, image generation is available through only one provider, OpenRouter.

 916 ## Stop Reasons
 917 
 918 Every `AssistantMessage` includes a `stopReason` field that indicates how the generation ended:
 919 
 920 - `"pending"` - Only present in partial messages when we do not know what the stop reason will be
 921 - `"stop"` - This is the final message the model will produce this turn
 922 - `"length"` - Output hit the maximum token limit
 923 - `"toolUse"` - Model is calling tools and expects tool results
 924 - `"error"` - An error occurred during generation
 925 - `"aborted"` - Request was cancelled via abort signal
 926 
 927 `AssistantMessage` may also include `responseId`, a provider-specific upstream response or message identifier when the underlying API exposes one. Do not assume it is always present across providers.

 929 ## Error Handling
 930 
 931 Request failures after a stream is returned never throw: when a request ends with an error (including aborts and tool call validation errors), the streaming API emits an error event and the final message carries the details. Setup failures may emit `error` without `start`; failures after generation begins emit `start`, any observed updates, then `error`. Direct API `streamSimple()` calls throw synchronously when request auth is missing:
 932 
 933 ```typescript
 934 // In streaming
 935 for await (const event of s) {
 936   if (event.type === 'error') {
 937     // event.reason is either "error" or "aborted"
 938     // event.error is the AssistantMessage with partial content
 939     console.error(`Error (${event.reason}):`, event.error.errorMessage);
 940     console.log('Partial content:', event.error.content);
 941   }
 942 }
 943 
 944 // The final message will have the error details
 945 const message = await s.result();
 946 if (message.stopReason === 'error' || message.stopReason === 'aborted') {
 947   console.error('Request failed:', message.errorMessage);
 948   // message.content contains any partial content received before the error
 949   // message.usage contains partial token counts and costs
 950 }
 951 ```
 952 
 953 When using a provider collection, auth failures (OAuth refresh failed, unknown provider) surface as a stream error with `stopReason: "error"`. Direct API `streamSimple()` calls instead throw synchronously when their required auth is absent.

 960 const controller = new AbortController();

 972   if (event.type === 'text_delta') {

 975     // event.reason tells you if it was "error" or "aborted"

 977   }
 978 }
 979 
 980 // Get results (may be partial if aborted)
 981 const response = await s.result();
 982 if (response.stopReason === 'aborted') {
 983   console.log('Request was aborted:', response.errorMessage);
 984   console.log('Partial content received:', response.content);

1114 Dynamic model lists use `fetchModels`. `Models.refresh()` refreshes every configured dynamic provider, passing its effective API-key or refreshed OAuth credential. 1132 `Models.refresh()` is unbounded when its optional signal is omitted. Providers always receive a concrete `RefreshModelsContext.signal` and must honor it for network requests and other blocking work. When a caller supplies a signal, `Models.refresh()` returns promptly with `aborted: true` after cancellation even if a custom provider fails to cooperate; the provider must still honor the signal to stop its underlying work.

Omit `persist` to leave storage unchanged, pass a `ModelsStoreEntry` to write it, or pass `persist: null` to delete it. Publication is generation-checked; put synchronous in-memory catalog changes in `update` rather than mutating state before publication.

1202

1336 ## Cross-Provider Handoffs
1337 
1338 The library supports seamless handoffs between different LLM providers within the same conversation. This allows you to switch models mid-conversation while preserving context, including thinking blocks, tool calls, and tool results.
1339 
1340 When messages from one provider are sent to a different provider, the library automatically transforms them for compatibility:
1341 
1342 - **User and tool result messages** are passed through unchanged
1343 - **Assistant messages from the same provider/API** are preserved as-is
1344 - **Assistant messages from different providers** have their thinking blocks converted to text with `<thinking>` tags
1345 - **Tool calls and regular text** are preserved unchanged
1346 
1347 ```typescript
1348 import { createModels, type Context } from '@earendil-works/pi-ai';
1349 import { anthropicProvider } from '@earendil-works/pi-ai/providers/anthropic';
1350 import { openaiProvider } from '@earendil-works/pi-ai/providers/openai';
1351 import { googleProvider } from '@earendil-works/pi-ai/providers/google';
1352 
1353 const models = createModels();
1354 models.setProvider(anthropicProvider());
1355 models.setProvider(openaiProvider());
1356 models.setProvider(googleProvider());
1357 
1358 const context: Context = { messages: [] };
1359 
1360 // Start with Claude
1361 const claude = models.getModel('anthropic', 'claude-sonnet-4-5')!;
1362 context.messages.push({ role: 'user', content: 'What is 25 * 18?', timestamp: Date.now() });
1363 context.messages.push(await models.completeSimple(claude, context, { reasoning: 'medium' }));
1364 
1365 // Switch to GPT-5 - it will see Claude's thinking as <thinking> tagged text
1366 const gpt5 = models.getModel('openai', 'gpt-5-mini')!;
1367 context.messages.push({ role: 'user', content: 'Is that calculation correct?', timestamp: Date.now() });
1368 context.messages.push(await models.complete(gpt5, context));
1369 
1370 // Switch to Gemini
1371 const gemini = models.getModel('google', 'gemini-2.5-flash')!;
1372 context.messages.push({ role: 'user', content: 'What was the original question?', timestamp: Date.now() });
1373 const geminiResponse = await models.complete(gemini, context);
1374 ```
1375 
1376 All providers can handle messages from other providers — text, tool calls and results (including images), thinking blocks (transformed to tagged text), and aborted messages with partial content. This enables flexible workflows: start with a fast model, switch to a more capable one for complex reasoning, or maintain continuity across provider outages.

1378 ## System Messages
1379 
1380 `Context.systemPrompt` and `Context.tools` are shorthand for a leading system message. The public entry points (`Models.stream()`, `streamSimple()`, `complete()`, `completeSimple()`) accept a `Context` and call `normalizeContext()` once; everything below them, including `Provider.stream()`, `ProviderStreams`, and the API implementation modules, receives the resulting `TranscriptContext`, which only has `messages`. The transcript can also carry system messages later in the conversation to change the prompt or the tool set without rewriting the history:
1381 
1382 ```typescript
1383 interface SystemMessage {
1384   role: "system";
1385   content: string | TextContent[];             // leading: base prompt; later: added instructions
1386   sections?: Record<string, string | null>;    // named prompt sections; later messages patch by name, null removes
1387   toolsAdded?: Tool[];                         // tools that become available here
1388   toolsRemoved?: ToolReference[];              // tools that stop being available here
1389   timestamp: number;
1390 }
1391 ```
1392 
1393 Sections are opaque text rendered verbatim after `content`, joined by blank lines. Keep each one self-delimiting (a tag, a heading) so the model can relate an update to the original. Replaying every system message in order yields the current prompt and tools; the replay helpers take the message list:
1394 
1395 ```typescript
1396 import { getCurrentSystemPrompt, getCurrentTools } from "@earendil-works/pi-ai";
1397 
1398 const messages: Message[] = [
1399   { role: "system", content: "You are helpful.", sections: { rules: "<rules>Be brief.</rules>" }, toolsAdded: [readTool], timestamp: 1 },
1400   { role: "user", content: "hi", timestamp: 2 },
1401   { role: "system", content: "", sections: { rules: "<rules>Be thorough.</rules>" }, toolsRemoved: [{ name: "read" }], timestamp: 3 },
1402 ];
1403 getCurrentSystemPrompt(messages); // "You are helpful.\n\n<rules>Be thorough.</rules>"
1404 getCurrentTools(messages);        // []
1405 ```
1406 
1407 A custom `Provider` or `ProviderStreams` implementation reads the prompt and tools the same way from `context.messages`; `context.systemPrompt` and `context.tools` do not exist at that layer.
1408 
1409 Models that accept system messages mid-conversation (`supportsMidConvoSystemMessages` in the model's compat settings, set by the generated catalog for verified models) receive each later system message in place, so the cached prefix stays intact; section changes are framed by name for the model. Every other model receives `collapseSystemMessages(transcript)`: the replayed prompt and current tools as the leading system message, with later system messages dropped. Anthropic models that also set `supportsMidConvoToolChanges` send tool changes as native `tool_addition`/`tool_removal` blocks: the initial tools stay active at the top level, every later declaration is sent with `defer_loading` (plus a stable deferred placeholder from the first request, which keeps Anthropic's deferred-tool scaffolding in the cached prefix), and removed tools stay declared, so tool changes do not invalidate the prompt cache. That needs at least one initial tool and no same-name redefinition; otherwise the current tool list is sent at the top level with the system text only. OpenAI Responses models with `supportsAdditionalTools` or `supportsToolSearch` anchor additive tool changes at their message; everything else sends the current tool list at the top level.

1412 
1413 The `Context` object can be easily serialized and deserialized using standard JSON methods, making it simple to persist conversations, implement chat history, or transfer contexts between services:

1415 ```typescript
1416 const context: Context = {
1417   systemPrompt: 'You are a helpful assistant.',
1418   messages: [
1419     { role: 'user', content: 'What is TypeScript?', timestamp: Date.now() }

1428 const serialized = JSON.stringify(context);

1431 localStorage.setItem('conversation', serialized);
1432

1480 
1481 const models = createModels();
1482 models.setProvider(openaiProvider());
1483 ```

1485 Rules:
1486 
1487 - `@earendil-works/pi-ai` is the core entrypoint and does not import built-in catalogs, provider factories, or SDK implementations.
1488 - `@earendil-works/pi-ai/providers/<provider>` imports that provider's catalog and lazy API wrapper only.
1489 - `@earendil-works/pi-ai/providers/all` imports every built-in provider factory and all catalogs. Use it only when you want the full built-in set.
1490 - With code splitting, provider SDKs stay in lazy chunks and load on first request.
1491 - Without code splitting, bundlers fold reachable lazy API implementations into the single bundle. A single-provider bundle then includes that provider's SDK; `providers/all` includes all statically visible SDKs. Bedrock is the exception: its AWS SDK implementation is loaded through a bundler-opaque Node-only import.
1492 - Importing `@earendil-works/pi-ai/api/<api-id>` directly loads that API implementation and its SDK immediately.
1493 
1494 Avoid `@earendil-works/pi-ai/compat` in new bundled apps; it preserves the old global API and imports the full built-in catalog surface.
1495 
1496 For single-file Node ESM bundles, some SDK dependencies may still use dynamic CommonJS `require()` internally. If you see errors such as `Dynamic require of "child_process" is not supported`, add a Node `require` shim to the bundle. With esbuild:
1497 
1498 ```bash
1499 esbuild app.js --bundle --platform=node --format=esm \
1500   --banner:js='import { createRequire } from "module";const require = createRequire(import.meta.url);' \
1501   --outfile=app.bundle.js
1502 ```
1503 
1504 This is only for Node bundles; it is not a browser or Cloudflare Workers workaround.

1506 Bedrock is Node-only. Add it like any other provider:
1507 
1508 ```typescript
1509 import { createModels } from '@earendil-works/pi-ai';
1510 import { amazonBedrockProvider } from '@earendil-works/pi-ai/providers/amazon-bedrock';

1517

1521 
1522 setBedrockProviderModule(bedrockProviderModule);

1546 ## OAuth Providers
1547 
1548 Several providers support OAuth authentication instead of static API keys:
1549 
1550 - **Anthropic** (Claude Pro/Max subscription)
1551 - **OpenAI Codex** (ChatGPT Plus/Pro subscription, access to GPT-5.x Codex models)
1552 - **GitHub Copilot** (Copilot subscription)
1553 - **OpenRouter** (OAuth PKCE that mints a user-controlled API key)
1554 
1555 Each of these providers carries an `OAuthAuth` on `provider.auth.oauth` with three operations: `login(interaction)` uses the provider-neutral `AuthInteraction.prompt()`/`notify()` protocol and returns a credential, `refresh(credential, signal)` refreshes expiring credentials when applicable, and `toAuth(credential)` derives request auth (GitHub Copilot's per-account base URL comes from here). Provider login interactions and refresh calls always carry a concrete abort signal. Refresh is automatic: `models.getAuth(providerId)` and request paths refresh expired tokens under a credential-store lock, so concurrent requests and processes cannot double-refresh. OpenRouter's OAuth flow instead returns a permanent API key, so its refresh operation is a no-op.
1556 
1557 ```typescript
1558 import { createModels } from '@earendil-works/pi-ai';
1559 import { anthropicProvider } from '@earendil-works/pi-ai/providers/anthropic';
1560 
1561 const models = createModels({ credentials: myStore }); // persistent CredentialStore
1562 models.setProvider(anthropicProvider());
1563 
1564 // Login: Models drives the flow and persists the credential
1565 await models.login('anthropic', 'oauth', {
1566   prompt: async (p) => {
1567     // p.type: 'text' | 'secret' | 'select' | 'manual_code'
1568     // manual_code prompts race a local callback server; p.signal aborts them when the server wins
1569     return await askUser(p.message);
1570   },
1571   notify: (event) => {
1572     // event.type: 'info' | 'auth_url' | 'device_code' | 'progress'
1573     if (event.type === 'info') {
1574       console.log(event.message);
1575       for (const link of event.links ?? []) console.log(`${link.label ?? 'More information'}: ${link.url}`);
1576     }
1577     if (event.type === 'auth_url') console.log(`Open: ${event.url}`);
1578     if (event.type === 'device_code') console.log(`Code: ${event.userCode} at ${event.verificationUri}`);
1579     if (event.type === 'progress') console.log(event.message);
1580   },
1581 });
1582 
1583 // From here on, requests resolve and refresh the token automatically
1584 const model = models.getModel('anthropic', 'claude-sonnet-4-5')!;
1585 await models.complete(model, context);
1586 
1587 // Logout
1588 await models.logout('anthropic');
1589 ```

1593 Vertex AI models support either a Google Cloud API key or Application Default Credentials (ADC). Its provider-owned API-key login flow can configure either method:

1595 - **API key**: Set `GOOGLE_CLOUD_API_KEY` or pass `apiKey` in the call options.

1602 # Local (uses your user credentials)
1603 gcloud auth application-default login
1604 export GOOGLE_CLOUD_PROJECT="my-project"
1605 export GOOGLE_CLOUD_LOCATION="us-central1"
1606 
1607 # CI/Production (service account key file)
1608 export GOOGLE_APPLICATION_CREDENTIALS="/path/to/service-account.json"

1629 Provider notes:
1630 
1631 **OpenAI Codex**: Requires a ChatGPT Plus or Pro subscription. Provides access to GPT-5.x Codex models with extended context windows and reasoning capabilities. The library automatically handles session-based prompt caching when `sessionId` is provided in stream options unless `cacheRetention` is `"none"`. You can set `transport` in stream options to `"sse"`, `"websocket"`, or `"auto"` for Codex Responses transport selection. When using WebSocket with a `sessionId` and cache retention enabled, connections are reused per session and expire after 5 minutes of inactivity. Call `cleanupSessionResources(sessionId)` when finished so the pooled connection does not keep the process alive.
1632 
1633 **Azure OpenAI (Responses)**: Uses the Responses API only. Set `AZURE_OPENAI_API_KEY` and either `AZURE_OPENAI_BASE_URL` or `AZURE_OPENAI_RESOURCE_NAME`. `AZURE_OPENAI_BASE_URL` supports both `https://<resource>.openai.azure.com` and `https://<resource>.cognitiveservices.azure.com`; root endpoints are normalized to `.../openai/v1` automatically. Use `AZURE_OPENAI_API_VERSION` (defaults to `v1`) to override the API version if needed. Deployment names are treated as model IDs by default, override with `azureDeploymentName` or `AZURE_OPENAI_DEPLOYMENT_NAME_MAP` using comma-separated `model-id=deployment` pairs (for example `gpt-4o-mini=my-deployment,gpt-4o=prod`). Legacy deployment-based URLs are intentionally unsupported.

1637 ## Migrating from the Old Global API
1638 
1639 Older versions exposed a global API: `stream()`/`complete()` dispatching on `model.api` via a global registry, sync `getModel()`/`getModels()`/`getProviders()` catalog reads, `registerApiProvider()`, `getEnvApiKey()`, and per-API lazy stream functions. That surface lives unchanged on the **compat entrypoint**:
1640 
1641 ```typescript
1642 // Before
1643 import { getModel, complete } from '@earendil-works/pi-ai';
1644 
1645 // After (verbatim behavior, one import-path change)
1646 import { getModel, complete } from '@earendil-works/pi-ai/compat';
1647 ```
1648 
1649 Compat is a strict superset of the root entrypoint, so a file can switch its import path wholesale. It will be removed in a future release; migrate to `createModels()` + provider factories:
1650 
1651 | Old | New |
1652 |-----|-----|
1653 | `getModel('openai', 'gpt-4o-mini')` | `models.getModel('openai', 'gpt-4o-mini')` or `getBuiltinModel()` from `providers/all` |
1654 | `getModels('anthropic')` / `getProviders()` | `models.getModels('anthropic')` / `models.getProviders()` or `getBuiltin*` |
1655 | `stream(model, ctx, opts)` (env-key injection) | `models.stream(model, ctx, opts)` (provider auth resolution) |
1656 | `registerApiProvider({ api, stream, streamSimple })` | `createProvider({ id, auth, models, api })` + `models.setProvider()` |
1657 | `getEnvApiKey('openai')` | `await models.getAuth(model.provider)` |
1658 | `streamAnthropic(model, ctx, opts)` | `stream` from `@earendil-works/pi-ai/api/anthropic-messages`, or a provider in a collection |
1659 | `registerFauxProvider()` | `fauxProvider()` + `models.setProvider()` |

1663 ### Adding a New Provider
1664 
1665 Adding a new LLM provider requires changes across multiple files. The layered layout: API implementations live in `src/api/`, provider factories in `src/providers/`, stable generated catalog wrappers live in `src/providers/<id>.models.ts`, and `src/models.generated.ts` registers them. This checklist covers all necessary steps:
1666 
1667 #### 1. Core Types (`src/types.ts`)
1668 
1669 - Add the API identifier to `KnownApi` (for example `"bedrock-converse-stream"`), if it is a new API
1670 - Add the provider name to `KnownProvider` (for example `"amazon-bedrock"`)
1671 - Add the options type to `ApiOptionsMap`
1672 
1673 #### 2. API Implementation (`src/api/<api-id>.ts`, only for a new API)
1674 
1675 Create a new API implementation file (for example `bedrock-converse-stream.ts`) that exports exactly `stream` and `streamSimple`, plus:
1676 
1677 - An options interface extending `StreamOptions` (for example `BedrockOptions`)
1678 - Message conversion functions to transform the `TranscriptContext` messages to provider format; read the prompt and tools from the transcript with `getInitialSystemMessage()`, `getCurrentTools()`, and `resolveTranscript()`
1679 - Tool conversion if the provider supports tools
1680 - Response parsing to emit standardized events (`text`, `tool_call`, `thinking`, `usage`, `stop`)
1681 
1682 Add a lazy wrapper `src/api/<api-id>.lazy.ts` (`<name>Api()` via `lazyApi()`) so providers can reference the implementation without importing its SDK. Add any root-level `export type` re-exports in `src/index.ts` that should remain available from `@earendil-works/pi-ai`.
1683 
1684 #### 3. Model Generation (`scripts/generate-models.ts`, `scripts/generate-image-models.ts`)
1685 
1686 - Add logic to fetch and parse models from the provider's source (e.g., models.dev API)
1687 - Map chat/tool-capable provider model data to the standardized `Model` interface via `scripts/generate-models.ts`; hydration groups the ignored `src/providers/data/<id>.json` values by API, while stable `src/providers/<id>.models.ts` wrappers derive exact model/API types directly from those JSON keys
1688 - Map image-generation provider model data to the standardized `ImagesModel` interface via `scripts/generate-image-models.ts`
1689 - Handle provider-specific quirks (pricing format, capability flags, model ID transformations)
1690 
1691 #### 4. Provider Factory (`src/providers/<id>.ts`)
