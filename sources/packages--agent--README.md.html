   1 # @earendil-works/pi-agent-core
   2 
   3 Stateful agent with tool execution and event streaming. Built on `@earendil-works/pi-ai`.
   4 
   5 ## Installation
   6 
   7 ```bash
   8 npm install @earendil-works/pi-agent-core
   9 ```
  10 
  11 ### SQLite session backends
  12 
  13 The SQLite session backend and the `node:sqlite` adapter live in a separate package, `@earendil-works/pi-session-backend-sqlite-node`, so the core package does not pull in runtime builtins or native SQLite dependencies by default. The backend accepts a runtime-specific SQLite factory, allowing other session backends to ship as their own packages in the future.
  14 
  15 ## Quick Start
  16 
  17 ```typescript
  18 import { Agent } from "@earendil-works/pi-agent-core";
  19 import { createModels } from "@earendil-works/pi-ai";
  20 import { anthropicProvider } from "@earendil-works/pi-ai/providers/anthropic";
  21 
  22 const models = createModels();
  23 models.setProvider(anthropicProvider());
  24 const model = models.getModel("anthropic", "claude-sonnet-4-6");
  25 if (!model) throw new Error("Model not found");
  26 
  27 const agent = new Agent({
  28   initialState: {
  29     systemPrompt: "You are a helpful assistant.",
  30     model,
  31   },
  32   streamFn: models.streamSimple.bind(models),
  33 });
  34 
  35 agent.subscribe((event) => {
  36   if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
  37     // Stream just the new text chunk
  38     process.stdout.write(event.assistantMessageEvent.delta);
  39   }
  40 });
  41 
  42 await agent.prompt("Hello!");
  43 ```

  49 ## Core Concepts
  50 
  51 ### AgentMessage vs LLM Message
  52 
  53 The agent works with `AgentMessage`, a flexible type that can include:
  54 - Standard LLM messages (`user`, `assistant`, `toolResult`)
  55 - Custom app-specific message types via declaration merging
  56 
  57 LLMs only understand `user`, `assistant`, and `toolResult`. The `convertToLlm` function bridges this gap by filtering and transforming messages before each LLM call.
  58 
  59 ### Message Flow
  60 
  61 ```
  62 AgentMessage[] → transformContext() → AgentMessage[] → convertToLlm() → Message[] → LLM
  63                     (optional)                           (required)
  64 ```
  65 
  66 1. **transformContext**: Prune old messages, inject external context
  67 2. **convertToLlm**: Filter out UI-only messages, convert custom types to LLM format
  68 
  69 ## Event Flow
  70 
  71 The agent emits events for UI updates. Understanding the event sequence helps build responsive interfaces.
  72 
  73 ### prompt() Event Sequence
  74 
  75 When you call `prompt("Hello")`:
  76 
  77 ```
  78 prompt("Hello")
  79 ├─ agent_start
  80 ├─ turn_start
  81 ├─ message_start   { message: userMessage }      // Your prompt
  82 ├─ message_end     { message: userMessage }
  83 ├─ message_start   { message: assistantMessage } // LLM starts responding
  84 ├─ message_update  { message: partial... }       // Streaming chunks
  85 ├─ message_update  { message: partial... }
  86 ├─ message_end     { message: assistantMessage } // Complete response
  87 ├─ turn_end        { message, toolResults: [] }
  88 └─ agent_end       { messages: [...] }
  89 ```
  90 
  91 ### With Tool Calls
  92 
  93 If the assistant calls tools, the loop continues:
  94 
  95 ```
  96 prompt("Read config.json")
  97 ├─ agent_start
  98 ├─ turn_start
  99 ├─ message_start/end  { userMessage }
 100 ├─ message_start      { assistantMessage with toolCall }
 101 ├─ message_update...
 102 ├─ message_end        { assistantMessage }
 103 ├─ tool_execution_start  { toolCallId, toolName, args }
 104 ├─ tool_execution_update { partialResult }           // If tool streams
 105 ├─ tool_execution_end    { toolCallId, result }
 106 ├─ message_start/end  { toolResultMessage }
 107 ├─ turn_end           { message, toolResults: [toolResult] }
 108 │
 109 ├─ turn_start                                        // Next turn
 110 ├─ message_start      { assistantMessage }           // LLM responds to tool result
 111 ├─ message_update...
 112 ├─ message_end
 113 ├─ turn_end
 114 └─ agent_end
 115 ```
 116 
 117 Tool execution mode is configurable:
 118 
 119 - `parallel` (default): preflight tool calls sequentially, execute allowed tools concurrently, emit `tool_execution_end` as soon as each tool is finalized, then emit toolResult messages and `turn_end.toolResults` in assistant source order
 120 - `sequential`: execute tool calls one by one, matching the historical behavior
 121 
 122 In parallel mode, tool completion events follow tool completion order, but persisted toolResult messages still follow assistant source order.
 123 
 124 The mode can be set globally via `toolExecution` in the agent config, or per-tool via `executionMode` on `AgentTool`. If any tool call in a batch targets a tool with `executionMode: "sequential"`, the entire batch executes sequentially regardless of the global setting.
 125 
 126 The `beforeToolCall` hook runs after `tool_execution_start` and validated argument parsing. It can block execution and attach `terminate: true` to the blocked result. The `afterToolCall` hook runs after tool execution finishes and before `tool_execution_end` and final tool result message events are emitted.
 127 
 128 Tools, blocked `beforeToolCall` results, and `afterToolCall` overrides can return `terminate: true` to hint that the automatic follow-up LLM call should be skipped. The loop only stops early when every finalized tool result in that batch sets `terminate: true`. Mixed batches continue normally.
 129 
 130 The `Agent` class accepts `shouldStopAfterTurn` in `AgentOptions`. Low-level loop callers can set the same hook in `AgentLoopConfig`:
 131 
 132 ```typescript
 133 const stream = agentLoop(
 134   prompts,
 135   context,
 136   {
 137     model,
 138     convertToLlm,
 139     shouldStopAfterTurn: async ({ message, toolResults, context, newMessages }) => {
 140       return shouldCompactBeforeNextTurn(context.messages);
 141     },
 142   },
 143   undefined,
 144   models.streamSimple.bind(models),
 145 );
 146 ```
 147 
 148 `shouldStopAfterTurn` runs after `turn_end` is emitted and after the assistant response and any tool executions have completed normally. If it returns `true`, the loop emits `agent_end` and exits before polling steering or follow-up queues, and before starting another LLM call. It does not abort the provider stream, does not cancel running tools, and does not alter the assistant message stop reason. The `AgentOptions` callback also receives the active run's `AbortSignal` as its second argument.
 149 
 150 When you use the `Agent` class, assistant `message_end` processing is treated as a barrier before tool preflight begins. That means `beforeToolCall` sees agent state that already includes the assistant message that requested the tool call.
 151 
 152 ### continue() Event Sequence
 153 
 154 `continue()` resumes from existing context without adding a new message. Use it for retries after errors.
 155 
 156 ```typescript
 157 // After an error, retry from current state
 158 await agent.continue();
 159 ```
 160 
 161 The last message in context must be `user` or `toolResult` (not `assistant`).
 162 
 163 ### Event Types
 164 
 165 | Event | Description |
 166 |-------|-------------|
 167 | `agent_start` | Agent begins processing |
 168 | `agent_end` | Final event for the run. Awaited subscribers for this event still count toward settlement |
 169 | `turn_start` | New turn begins (one LLM call + tool executions) |
 170 | `turn_end` | Turn completes with assistant message and tool results |
 171 | `message_start` | Any message begins (user, assistant, toolResult) |
 172 | `message_update` | **Assistant only.** Includes `assistantMessageEvent` with delta |
 173 | `message_end` | Message completes |
 174 | `tool_execution_start` | Tool begins |
 175 | `tool_execution_update` | Tool streams progress |
 176 | `tool_execution_end` | Tool completes |
 177 
 178 `Agent.subscribe()` listeners are awaited in registration order. `agent_end` means no more loop events will be emitted, but `await agent.waitForIdle()` and `await agent.prompt(...)` only settle after awaited `agent_end` listeners finish.

 180 ## Agent Options
 181 
 182 ```typescript
 183 const agent = new Agent({
 184   // Initial state. systemPrompt and tools become the leading system message
 185   // unless messages already starts with one.
 186   initialState: {
 187     systemPrompt: string,
 188     model: Model<any>,
 189     thinkingLevel: "off" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max",
 190     tools: AgentTool<any>[],
 191     messages: AgentMessage[],
 192   },
 193 
 194   // Convert AgentMessage[] to LLM Message[] (required for custom message types)
 195   convertToLlm: (messages) => messages.filter(...),
 196 
 197   // Transform context before convertToLlm (for pruning, compaction)
 198   transformContext: async (messages, signal) => pruneOldMessages(messages),
 199 
 200   // Steering mode: "one-at-a-time" (default) or "all"
 201   steeringMode: "one-at-a-time",
 202 
 203   // Follow-up mode: "one-at-a-time" (default) or "all"
 204   followUpMode: "one-at-a-time",
 205 
 206   // Required stream function. Receives a TranscriptContext: the prompt and tools
 207   // are in the transcript's system messages, not on the context.
 208   streamFn: models.streamSimple.bind(models),
 209 
 210   // Session ID for provider caching
 211   sessionId: "session-123",
 212 
 213   // Dynamic API key resolution (for expiring OAuth tokens)
 214   getApiKey: async (provider) => refreshToken(),
 215 
 216   // Tool execution mode: "parallel" (default) or "sequential"
 217   toolExecution: "parallel",
 218 
 219   // Preflight each tool call after args are validated. Can block execution.
 220   beforeToolCall: async ({ toolCall, args, context }) => {
 221     if (toolCall.name === "bash") {
 222       return { block: true, reason: "bash is disabled", terminate: true };
 223     }
 224   },
 225 
 226   // Postprocess each tool result before final tool events are emitted.
 227   afterToolCall: async ({ toolCall, result, isError, context }) => {
 228     if (toolCall.name === "notify_done" && !isError) {
 229       return { terminate: true };
 230     }
 231     if (!isError) {
 232       return { details: { ...result.details, audited: true } };
 233     }
 234   },
 235 
 236   // Stop gracefully after a completed turn, before queued messages are polled.
 237   shouldStopAfterTurn: async ({ context }, signal) => {
 238     return shouldCompactBeforeNextTurn(context.messages, signal);
 239   },
 240 
 241   // Custom thinking budgets for token-based providers
 242   thinkingBudgets: {
 243     minimal: 128,
 244     low: 512,
 245     medium: 1024,
 246     high: 2048,
 247   },
 248 });
 249 ```

 251 ## Agent State
 252 
 253 ```typescript
 254 interface AgentState {
 255   model: Model<any>;
 256   thinkingLevel: ThinkingLevel;
 257   tools: AgentTool<any>[];
 258   messages: AgentMessage[];
 259   readonly isStreaming: boolean;
 260   readonly streamingMessage?: AgentMessage;
 261   readonly pendingToolCalls: ReadonlySet<string>;
 262   readonly errorMessage?: string;
 263 }
 264 ```
 265 
 266 Access state via `agent.state`.
 267 
 268 Assigning `agent.state.tools = [...]` or `agent.state.messages = [...]` copies the top-level array before storing it. Mutating the returned array mutates the current agent state.
 269 
 270 The transcript owns the system prompt and tool declarations: the leading system message is the prompt, later system messages patch it (see `SystemMessage` in pi-ai). `agent.state.systemPrompt` is read-only and replays the transcript. `agent.state.tools` is the executable loadout; before every request the loop diffs it against the tools the transcript declares and, if they differ, announces the change in a system message (merged into a pending system message when one exists). pi-ai's `getCurrentSystemMessage(messages)` returns the replayed head, including declared tools, for any message array, including agent transcripts with custom message roles.
 271 
 272 To change the prompt mid-conversation, append a system message with `content` (added instructions) or `sections` (named replacements):
 273 
 274 ```typescript
 275 await agent.prompt([
 276   { role: "system", content: "", sections: { skills: "<skills>...</skills>" }, timestamp: Date.now() },
 277   { role: "user", content: "Continue", timestamp: Date.now() },
 278 ]);
 279 ```
 280 
 281 During streaming, `agent.state.streamingMessage` contains the current partial assistant message.
 282 
 283 `agent.state.isStreaming` remains `true` until the run fully settles, including awaited `agent_end` subscribers.

 352 ## Steering and Follow-up
 353 
 354 Steering messages let you interrupt the agent while tools are running. Follow-up messages let you queue work after the agent would otherwise stop.
 355 
 356 ```typescript
 357 agent.steeringMode = "one-at-a-time";
 358 agent.followUpMode = "one-at-a-time";
 359 
 360 // While agent is running tools
 361 agent.steer({
 362   role: "user",
 363   content: "Stop! Do this instead.",
 364   timestamp: Date.now(),
 365 });
 366 
 367 // After the agent finishes its current work
 368 agent.followUp({
 369   role: "user",
 370   content: "Also summarize the result.",
 371   timestamp: Date.now(),
 372 });
 373 
 374 const steeringMode = agent.steeringMode;
 375 const followUpMode = agent.followUpMode;
 376 
 377 agent.clearSteeringQueue();
 378 agent.clearFollowUpQueue();
 379 agent.clearAllQueues();
 380 ```
 381 
 382 Use clearSteeringQueue, clearFollowUpQueue, or clearAllQueues to drop queued messages.
 383 
 384 When steering messages are detected after a turn completes:
 385 1. All tool calls from the current assistant message have already finished
 386 2. Steering messages are injected
 387 3. The LLM responds on the next turn
 388 
 389 Follow-up messages are checked only when there are no more tool calls and no steering messages. If any are queued, they are injected and another turn runs.

 391 ## Custom Message Types
 392 
 393 Extend `AgentMessage` via declaration merging:
 394 
 395 ```typescript
 396 declare module "@earendil-works/pi-agent-core" {
 397   interface CustomAgentMessages {
 398     notification: { role: "notification"; text: string; timestamp: number };
 399   }
 400 }
 401 
 402 // Now valid
 403 const msg: AgentMessage = { role: "notification", text: "Info", timestamp: Date.now() };
 404 ```
 405 
 406 Handle custom types in `convertToLlm`:
 407 
 408 ```typescript
 409 const agent = new Agent({
 410   streamFn: models.streamSimple.bind(models),
 411   convertToLlm: (messages) => messages.flatMap(m => {
 412     if (m.role === "notification") return []; // Filter out
 413     return [m];
 414   }),
 415 });
 416 ```

 418 ## Tools
 419 
 420 Define tools using `AgentTool`:
 421 
 422 ```typescript
 423 import { Type } from "typebox";
 424 
 425 const readFileTool: AgentTool = {
 426   name: "read_file",
 427   label: "Read File",  // For UI display
 428   description: "Read a file's contents",
 429   parameters: Type.Object({
 430     path: Type.String({ description: "File path" }),
 431   }),
 432   // Override execution mode for this tool (optional).
 433   // "sequential" forces the entire batch to run one at a time.
 434   // "parallel" allows concurrent execution with other tool calls.
 435   // If omitted, the global toolExecution config applies.
 436   executionMode: "sequential",
 437   execute: async (toolCallId, params, signal, onUpdate) => {
 438     const content = await fs.readFile(params.path, "utf-8");
 439 
 440     // Optional: stream progress
 441     onUpdate?.({ content: [{ type: "text", text: "Reading..." }], details: {} });
 442 
 443     // Optional: add `terminate: true` here to skip the automatic follow-up LLM call
 444     // when every finalized tool result in the batch does the same.
 445     return {
 446       content: [{ type: "text", text: content }],
 447       details: { path: params.path, size: content.length },
 448     };
 449   },
 450 };
 451 
 452 agent.state.tools = [readFileTool];
 453 ```
 454 
 455 ### Error Handling
 456 
 457 **Throw an error** when a tool fails. Do not return error messages as content.
 458 
 459 ```typescript
 460 execute: async (toolCallId, params, signal, onUpdate) => {
 461   if (!fs.existsSync(params.path)) {
 462     throw new Error(`File not found: ${params.path}`);
 463   }
 464   // Return content only on success
 465   return { content: [{ type: "text", text: "..." }] };
 466 }
 467 ```
 468 
 469 Thrown errors are caught by the agent and reported to the LLM as tool errors with `isError: true`.
 470 
 471 Return `terminate: true` from `execute()`, a blocked `beforeToolCall`, or `afterToolCall` to hint that the agent should stop after the current tool batch. This only takes effect when every finalized tool result in the batch is terminating. The hint is runtime-only; emitted `toolResult` transcript messages remain standard LLM tool results.

 490 ## Low-Level API
 491 
 492 For direct control without the Agent class:
 493 
 494 ```typescript
 495 import { agentLoop, agentLoopContinue } from "@earendil-works/pi-agent-core";
 496 
 497 const context: AgentContext = {
 498   messages: [{ role: "system", content: "You are helpful.", timestamp: Date.now() }],
 499   tools: [],
 500 };
 501 
 502 const config: AgentLoopConfig = {
 503   model: getModel("openai", "gpt-4o"),
 504   convertToLlm: (msgs) => msgs.filter(m => ["user", "assistant", "toolResult"].includes(m.role)),
 505   toolExecution: "parallel",  // overridden by per-tool executionMode if set
 506   beforeToolCall: async ({ toolCall, args, context }) => undefined,
 507   afterToolCall: async ({ toolCall, result, isError, context }) => undefined,
 508 };
 509 
 510 const userMessage = { role: "user", content: "Hello", timestamp: Date.now() };
 511 
 512 const streamFn = models.streamSimple.bind(models);
 513 for await (const event of agentLoop([userMessage], context, config, undefined, streamFn)) {
 514   console.log(event.type);
 515 }
 516 
 517 // Continue from existing context
 518 for await (const event of agentLoopContinue(context, config, undefined, streamFn)) {
 519   console.log(event.type);
 520 }
 521 ```
 522 
 523 These low-level streams are observational. They preserve event order, but they do not wait for your async event handling to settle before later producer phases continue. If you need message processing to act as a barrier before tool preflight, use the `Agent` class instead of raw `agentLoop()` or `agentLoopContinue()`.
