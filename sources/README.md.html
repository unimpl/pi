  13 # Pi Agent Harness
  14 
  15 This is the home of the Pi agent harness project including our self extensible coding agent.
  16 
  17 * **[@earendil-works/pi-coding-agent](packages/coding-agent)**: Interactive coding agent CLI
  18 * **[@earendil-works/pi-agent-core](packages/agent)**: Agent runtime with tool calling and state management
  19 * **[@earendil-works/pi-ai](packages/ai)**: Unified multi-provider LLM API (OpenAI, Anthropic, Google, …)
  20 
  21 To learn more about Pi:
  22 
  23 * [Visit pi.dev](https://pi.dev), the project website with demos
  24 * [Read the documentation](https://pi.dev/docs/latest), but you can also ask the agent to explain itself

  40 ## Permissions & Containerization
  41 
  42 Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.
  43 
  44 If you need stronger boundaries, containerize or sandbox Pi. See [packages/coding-agent/docs/containerization.md](packages/coding-agent/docs/containerization.md) for three patterns:
  45 
  46 - **Gondolin extension**: keep `pi` and provider auth on the host while routing built-in tools and `!` commands into a local Linux micro-VM.
  47 - **Plain Docker**: run the whole `pi` process in a local container for simple isolation.
  48 - **OpenShell**: run the whole `pi` process in a policy-controlled sandbox.

  54 ## Development
  55 
  56 ```bash
  57 npm install --ignore-scripts  # Install all dependencies without running lifecycle scripts
  58 npm run build         # Refresh model data, then build all packages
  59 npm run build:offline # Rebuild using existing model data without network access
  60 npm run check         # Lint, format, and type check
  61 ./test.sh            # Run tests (skips LLM-dependent tests without API keys)
  62 ./pi-test.sh         # Run pi from sources (can be run from any directory)
  63 ```

  65 ## Building standalone binaries from release source
  66 
  67 GitHub releases include a versioned source archive covered by the release's `SHA256SUMS` file. Extract it and run the same build script used for the official standalone binaries:
  68 
  69 ```bash
  70 VERSION="<release-version>"
  71 tar -xzf "pi-${VERSION}-source.tar.gz"
  72 cd "pi-${VERSION}"
  73 ./scripts/build-binaries.sh --offline-model-data --platform linux-x64 --out "$PWD/out"
  74 ```
  75 
  76 The archive includes release model data and native prebuilds. `--offline-model-data` uses that model data without refreshing provider catalogs. The script installs dependencies and builds the executable with its runtime assets; pass `--skip-install` if dependencies are already provided.

  78 ## Supply-chain hardening
  79 
  80 We treat npm dependency changes as reviewed code changes.
  81 
  82 - Direct external dependencies are pinned to exact versions. Internal workspace packages remain version-ranged.
  83 - `.npmrc` sets `save-exact=true` and `min-release-age=2` to avoid same-day dependency releases during npm resolution.
  84 - `package-lock.json` is the dependency ground truth. Pre-commit blocks accidental lockfile commits unless `PI_ALLOW_LOCKFILE_CHANGE=1` is set.
  85 - `npm run check` verifies pinned direct deps, native TypeScript import compatibility, and the generated coding-agent shrinkwrap.
  86 - The published CLI package includes `packages/coding-agent/npm-shrinkwrap.json`, generated from the root lockfile, to pin transitive deps for npm users.
  87 - Release smoke tests use `npm run release:local` to build, pack, and create isolated npm and Bun installs outside the repo before tagging a release.
  88 - Local release installs, documented npm installs, and `pi update --self` use `--ignore-scripts` where supported.
  89 - CI installs with `npm ci --ignore-scripts`, and a scheduled GitHub workflow runs `npm audit --omit=dev` plus `npm audit signatures --omit=dev`.
  90 - Shrinkwrap generation has an explicit allowlist for dependency lifecycle scripts; new lifecycle-script deps fail checks until reviewed.

  92 ## Share your OSS coding agent sessions
  93 
  94 If you use Pi or other coding agents for open source work, please share your sessions.
  95 
  96 Public OSS session data helps improve coding agents with real-world tasks, tool use, failures, and fixes instead of toy benchmarks.
  97 
  98 For the full explanation, see [this post on X](https://x.com/badlogicgames/status/2037811643774652911).
  99 
 100 To publish sessions, use [`badlogic/pi-share-hf`](https://github.com/badlogic/pi-share-hf). Read its README.md for setup instructions. All you need is a Hugging Face account, the Hugging Face CLI, and `pi-share-hf`.
