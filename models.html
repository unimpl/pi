第 05 章 / 核心

从一个模型调用，推导 Pi 的类型

每个类型都应回答一个具体问题；最小实现不必复制完整的多供应商体系。

先忘掉 Pi 的类型名。一个最小 Agent 只需要把一组消息交给模型，再取得一条可判断是否结束的 assistant 消息。本章从这个最小接口出发：每遇到一个真实问题，才引入一个类型，并说明它在 Pi 中为何更复杂。

本章先抓什么

必须掌握最小契约
为什么需要
Agent 需要可靠区分文字、工具请求、工具结果和结束原因；产品还需要阻止某家模型 API 的字段与错误规则侵入执行循环。
行业常见做法
常见做法是统一消息与调用接口，在 provider adapter 中转换线路协议，并为供应商特有的续接数据保留扩展字段。单一模型应用也常先采用更小的接口。
自己实现时
首版保留结构化消息、停止原因、调用 ID 和一个模型调用边界。先接准一个 provider；流式、能力目录和兼容矩阵由真实需求逐步加入。
现在可以忽略
完整模型目录、所有 thinking 参数和同时兼容多家供应商。它们是产品覆盖面，不是工具循环成立的前提。

起点：最小模型边界只有一个函数

如果只支持一个固定模型、没有流式界面，可以先把模型边界写成下面这样。这里的 Promise 类似 Go 的异步调用结果，或 Rust 的 Future：

type ModelClient = (request: {
  messages: Message[];
  tools: Tool[];
  signal?: AbortSignal;
}) => Promise<AssistantMessage>;

这已经足以支撑工具循环：Harness 发送历史，得到 assistant 消息；若其中包含 toolCall，就执行工具、追加 toolResult，再调用一次。最小边界的重点不是函数名，而是四项语义：

  1. 输入是结构化消息，不是拼接后的一个字符串；
  2. 工具发送的是声明，不是本地的 execute 函数；
  3. 输出保留文本或 toolCall，并给出停止原因；
  4. 取消信号可以传到网络请求，但取消不等于回滚已经完成的工作。

Pi 的 StreamFn 是这个函数的流式、可替换版本。后面的类型都在解决这个简单接口投入真实产品后出现的问题。

为什么不能只用 string：模型返回的不总是文字

问题：一旦支持工具和图片，输入输出就不再是纯文本。assistant 可能同时返回文字、thinking 和多个 toolCall；工具结果还必须带 toolCallId 才能与请求配对。若所有内容都压成字符串，Harness 只能重新解析自然语言，无法可靠地区分“给用户的文字”和“要求宿主执行的动作”。

Pi 因此定义 Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage。TypeScript 的竖线表示联合类型：可以把它类比为 Rust 的 enum Message；在 Go 中则接近带 role 判别字段的一组结构体。每个消息再由带 type 的内容块组成。

类型它回答的问题最小 Agent 是否需要
UserMessage用户给了什么输入？需要
AssistantMessage模型生成了文字、推理块还是工具请求？为何停止？需要
ToolResultMessage哪次调用得到了什么真实结果？是否失败？使用工具时需要
SystemMessage从这一点开始，规则和可用工具是什么？可以先简化成单个 system prompt

usage 与 stopReason 不是 UI 装饰。length 表示响应可能被截断，不能把其中看似完整的工具参数直接执行；error 与 aborted 决定循环应停止；usage 用于预算与观测。首版至少保留 stop reason，准备上线或控制成本时再完整记录 usage。

为什么 Model 不是模型客户端：配置与行为分开

问题：执行循环既要知道“调用哪个模型”，又要知道上下文窗口、最大输出、输入模态和推理能力。如果把这些判断写进 OpenAI 或 Anthropic 客户端，Agent 会依赖具体 SDK；测试时也难以替换。

Pi 的 Model 是一份模型描述数据，不是会自己发请求的对象。它保存 id、provider、api、baseUrl、contextWindow、maxTokens、输入能力和费用。真正的调用行为由 StreamFn 和 API 适配器提供。这个分离类似：

// Go 近似表达
type Model struct { ID, Provider, API string; ContextWindow int }
type StreamFn func(Model, Transcript) EventStream

provider 与 api 必须分开理解。provider 回答“服务由谁提供或部署”，api 回答“线路上使用哪种协议”。某个云服务可以提供 OpenAI-compatible API；同一 provider 也可能暴露多种 API。若按 provider 名直接选择请求格式，部署来源与协议形状会被绑死。

对只支持一个固定模型的首版，你甚至可以不定义完整 Model：把 model ID 和上下文上限放入客户端配置即可。出现第二个模型、需要运行时切换或需要按能力裁剪输入时，再把它提升成独立数据类型。

为什么有多层转换：变化来自三个方向

Pi 的调用路径看起来比最小函数多，是因为它同时面对三种独立变化：

变化Pi 的边界不分开会怎样
产品消息变化AgentMessage → convertToLlmUI 通知、压缩摘要等本地消息泄漏到模型协议
本次上下文变化transformContext裁剪、摘要和上下文注入散落在 provider 代码中
供应商协议变化normalizeContext → API adapterAgent 循环充满每家 API 的 system、tool 和参数分支

Context 是方便调用者构造的输入，可以分别给出 systemPrompt、messages 和 tools。TranscriptContext 是规范化结果：规则和工具声明已经进入有序 transcript。它带一个仅供编译器识别的 brand，防止开发者误把尚未规范化的 Context 传进 provider；这不是运行时安全检查。

为什么 Pi 把 system 和工具变化写入 transcript？例如第 1 turn 只有 read，第 3 turn 才加入 write。重放消息时可以解释每个时刻模型看到了哪些能力，也能把同一事实转换成不同 provider 接受的线路格式。可执行的 AgentTool.execute 仍只留在宿主进程，因为函数不能发送给模型服务。

最小实现判断：若你的应用消息就是模型消息，不需要自定义 UI 事件，也暂时不做压缩，那么 convertToLlm 和 transformContext 都可以是恒等操作，甚至先不单独命名。要保留的是“进入 provider 前只有一个转换点”，以免协议分支扩散进循环。

为什么需要 StreamFn 和事件流：过程与最终结果是两件事

问题：一次模型请求可能持续几十秒。终端要即时显示文本，取消要尽快下传，工具参数也可能分段到达；但 Agent 决定是否执行工具时又必须拿到一条完整、已结算的 assistant 消息。

Pi 用 StreamFn(model, context, options) → AssistantMessageEventStream 隔离这件事。Agent loop 只依赖这个函数，不直接依赖某家 SDK。事件流提供 text_delta 等过程事件，最后用 done 或 error 结算为完整 AssistantMessage。

因此事件流同时满足两个消费者：UI 消费增量以改善响应感；循环消费最终消息以维护状态机。只有 token 字符串流不够，因为调用者还需要知道内容块边界、工具参数何时完整、停止原因、用量和错误。

流式不是最小 Agent 的必要条件。第一版完全可以等待完整响应；当真实延迟影响使用、需要中途取消或需要展示工具调用进度时再加入。加入后必须定义 start、增量、done/error 的合法顺序，并保证任何失败路径都能结算，否则调用方可能永久等待。

Pi 的一个细节：事件里的 partial 是持续增长的同一个响应对象，不是每个时刻的不可变快照。若要保存历史帧，需要主动复制。TypeScript 的 readonly 也不能提供 Rust 所有权那样的运行时隔离。

为什么统一以后仍保留供应商字段

问题：统一得过头会损坏正确性。某些服务要求后续 turn 回传 response ID、thinking signature 或 tool-call namespace；丢掉这些不透明字段，下一次请求可能无法续接推理、命中缓存或关联响应。

Pi 的做法是统一 Harness 真正依赖的语义，例如 role、内容块、usage 和 stopReason，同时在消息或 Model 的兼容配置中保留必要的 provider 数据。上层通常只负责原样保存和回传，不解释其内部含义。

这是一种“共同核心 + 受控逃生口”的设计。收益是 Agent 循环保持稳定，供应商能力仍可用；代价是统一类型不再纯净，compat 和可选字段会增长。行业里的统一模型 SDK 普遍面对同一取舍：完全统一会丢能力，完全透传又会让业务代码绑定供应商。

最小实现不要预先设计几十个兼容开关。先为一个 provider 实现准确转换，把原始或不透明的续接数据放进明确的扩展字段；接入第二个 provider 时，再根据真实差异提炼公共接口。

自己实现时：保留四个核心，推迟三类复杂度

优先级要设计的内容原因
首版必须结构化 Message；assistant 的 stopReason；toolCall/toolResult 关联；单一模型调用接口没有这些就无法可靠推进工具循环或判断结束
首版留边界provider 转换集中在一个模块；取消信号；错误归一化实现可以简单，但不能让协议细节散入 Harness
真实使用后加入流事件、usage 预算、Model 能力元数据、上下文规范化由延迟、成本、模型切换和长会话需求驱动
第二个 provider 后再抽象ApiOptionsMap、compat 矩阵、thinking level 映射、认证注册表只看一家 API 时很容易抽象出错误的共同点
暂时忽略完整模型目录、图片生成 API、所有供应商特有参数它们扩大覆盖面，不改变 Agent 的核心反馈循环

一个可用的最小目录可以只有 messages、model-client 和一个具体 provider 适配器。Harness 依赖 model-client，适配器负责把统一消息变成线路 JSON，再把响应还原成统一 assistant 消息。不要从复制 Pi 的 types.ts 开始；先写清自己的循环真正读取哪些字段。

Pi 值得学习的重点是依赖方向：Agent loop 依赖稳定的模型契约，provider 差异停在边界。Pi 的大量模型元数据、兼容选项和事件变体是多模型产品积累出的工程规模，不是“Agent 成立”所需的最低门槛。

查看参考答案
  1. 最小 Agent 的模型边界需要哪些输入和输出？ 输入至少是结构化消息和工具声明，并能携带取消信号；输出至少是一条结构化 assistant 消息，包含文本或 toolCall 以及 stopReason。使用工具时，后续 toolResult 必须用调用 ID 与请求关联。流式事件与完整 Model 目录可以后加。
  2. 为什么 Message 不能只是 string？ 模型输出可能同时包含文字、推理块和多个工具调用，工具结果还需记录调用 ID 与错误状态。字符串会丢失这些边界，迫使 Harness 从自然语言重新猜测结构。带 role/type 的联合类型让循环能确定性处理。
  3. Model 为什么是一份数据，而不是某家 SDK 客户端？ Agent 需要模型身份、上下文上限和能力来做选择与预算，但不应因此依赖具体网络 SDK。Pi 把描述数据放在 Model，把调用行为放在 StreamFn 和 provider adapter，二者可以独立替换和测试。
  4. provider 与 api 为什么不是同一个概念？ provider 是服务来源，api 是线路协议；一个 provider 可以使用兼容其他厂商的 API，也可能提供多种 API。只按 provider 名称分支会把部署来源和请求格式绑死。
  5. 为什么既需要 convertToLlm，又需要 provider 适配？最小实现都要有吗？ convertToLlm 处理应用自定义消息，provider adapter 处理线路协议。Pi 同时存在这两个变化轴，所以分层。若首版应用消息就是模型消息，convertToLlm 可以省略或使用恒等实现；provider 转换仍应集中在一个边界。
  6. 流式是 Agent 的必要条件吗？ 不是。最小实现可以等待完整 AssistantMessage。真实延迟需要即时显示、取消和工具进度时再引入流；引入后必须保证 start、增量、done/error 都有明确顺序和最终结算。
  7. 统一消息后，为什么仍保留 responseId、thinkingSignature 等字段？ 这些是不透明但必要的 provider 连续性数据。删除它们可能破坏后续 turn 的推理续接、缓存或响应关联。上层通常只保存并回传，不解释其内容。
  8. 自己复刻时，哪些 Pi 类型可以暂时忽略？ 完整模型目录、ApiOptionsMap、compat 矩阵、thinking level 映射和所有流事件变体都可推迟。先实现结构化 Message、stopReason、toolCall/toolResult 关联以及一个集中式 provider 调用边界。
